## 1. Executive Summary

Following **STEP 33.157**, all 412 approved test-data records (including all 94 test bills, 114 test receipts, 97 sequence reservations, and 97 idempotency records) were successfully removed from Cloud Firestore. However, when an operator enters `001` or `BILL-001` into the manual bill number field in [`Temple_Accounts-1.html`](file:///d:/Temple/Temple_Accounts-1.html), the billing form displays the real-time rejection message:

> **"❌ Number BILL-001 is already reserved/issued. Numbers cannot be reused."**

### Key Diagnostic Findings:

1. **Exact Source of Message:**  
   The message is generated by client-side real-time input handler [`validateManualBillNoInput(input)`](file:///d:/Temple/Temple_Accounts-1.html#L11111-L11152) at [Line 11134](file:///d:/Temple/Temple_Accounts-1.html#L11134). Secondary guards exist at [Line 11445](file:///d:/Temple/Temple_Accounts-1.html#L11445) (in `billingSubmitForm()`) and [Line 21951](file:///d:/Temple/Temple_Accounts-1.html#L21951) (in `fsCreateBillingWithAccounting()`).

2. **The Blocking Condition:**  
   The rejection is **NOT** caused by an existing reservation document (`system/res_1`), an existing bill (`billing/bill_1`), an existing receipt (`receipts/rcpt_1`), or an idempotency record (`system/op_*`). All of those documents were confirmed deleted during STEP 33.157.  
   Instead, the rejection is caused purely by a **counter logic comparison**:
   $$\text{parsed } (1) < \text{nextSeq } (101)$$
   The system counter document `system/counters` still holds `globalSequenceCounter: 100`. Therefore, `getNextGlobalSequenceNo()` returns $100 + 1 = 101$. Any manual input where $\text{parsed} < 101$ is programmatically declared "already reserved/issued."

3. **Number Interpretation:**  
   The displayed or typed `001` is parsed via [`parseGlobalNumber()`](file:///d:/Temple/Temple_Accounts-1.html#L7667) into integer `1`, which [`formatGlobalNumber(1, 'BILL-')`](file:///d:/Temple/Temple_Accounts-1.html#L7662) formats identically as `BILL-001`.

4. **Collision & Conflict Safety:**  
   Exhaustive inspection confirms that **no genuine, physical, or historical record conflicts with sequence 1 (`BILL-001` / `R-001`)**. Physical receipt records use separate namespaces (`res_phys_P*`, `res_phys_PU*`) with `seqNumber: null`, and zero physical receipts exist in the database.

5. **Operational Status:**  
   In compliance with instructions, **no live database writes, counter resets, code edits, or rule changes were made during this step**.

## 3. Analysis of Number Parsing: `001` vs. `BILL-001`

The parsing function [`parseGlobalNumber()`](file:///d:/Temple/Temple_Accounts-1.html#L7667-L7672) is defined as:

```javascript
function parseGlobalNumber(str) {
  if (typeof str === 'number') return (Number.isInteger(str) && str > 0) ? str : null;
  if (!str || typeof str !== 'string') return null;
  const match = str.trim().match(/^(?:BILL-|R-)?0*([1-9]\d*)$/i);
  return match ? parseInt(match[1], 10) : null;
}
```

### Parsing Evaluation Table:

| Input Value | Regex Pattern Match | Captured Group 1 (`[1-9]\d*`) | Integer Result (`parseInt`) | Formatted Output (`formatGlobalNumber`) |
| :--- | :--- | :---: | :---: | :---: |
| `"001"` | Matches `^(?:BILL-\|R-)?0*([1-9]\d*)$` | `"1"` | `1` | `BILL-001` |
| `"BILL-001"` | Matches `^(?:BILL-\|R-)?0*([1-9]\d*)$` | `"1"` | `1` | `BILL-001` |
| `"1"` | Matches `^(?:BILL-\|R-)?0*([1-9]\d*)$` | `"1"` | `1` | `BILL-001` |
| `"bill-1"` | Matches `^(?:BILL-\|R-)?0*([1-9]\d*)$` | `"1"` | `1` | `BILL-001` |
| `"R-001"` | Matches `^(?:BILL-\|R-)?0*([1-9]\d*)$` | `"1"` | `1` | `BILL-001` |

**Conclusion:**  
Typing `001`, `BILL-001`, or `1` is unambiguously interpreted as numeric sequence `1`.  
Because `1 < 101`, any representation of sequence 1 is rejected with the formatted string `BILL-001`.

### Why `system/counters` Was Left at 100

In the planning for STEP 33.153 through STEP 33.157:
1. The cleanup specification was strictly bounded to **transactional document deletion** (412 targets).
2. The execution safeguards explicitly prohibited mutating system singletons:
   > *"Counter Protection: `system/counters` must NEVER be deleted or reset."*  
   > *(STEP 33.157 Report, Section 6.3)*
3. As a result, `system/counters` retained its pre-cleanup value:
   ```json
   {
     "globalSequenceCounter": 100,
     "billingReceiptCounter": 100,
     "receiptCounter": 1020,
     "voucherCounter": 502,
     "billingPrefix": "BILL-",
     "receiptPrefix": "R-",
     "voucherPrefix": "V-"
   }
   ```
4. This intentional monotonicity invariant succeeded in protecting the system from uncoordinated resets, but left the next allocated sequence number at `101` (`BILL-101`), which directly conflicts with the user's intent to start fresh at `BILL-001`.
